# 市政采购公告档案

面向市政采购档案员的公告留存工具：输入公告号，从本地示范站采集招标公告正文与唯一附件，按站点修订号逐版留档。网站改稿、换附件、撤稿后，旧版仍可核对、下载。截标前还可发起**漏采核对**：逐页读取示范站公告目录，与档案中各公告的最高修订和撤稿状态对照，列出未入档、修订落后或撤稿状态不一致的公告及双方状态。

技术栈：FastAPI + SQLite；Docker Compose 同时启动档案应用与可在浏览器改稿的本地示范站。

## 快速开始（Docker Compose）

```bash
docker compose up --build -d
```

- 示范站（可改稿/换附件/撤稿）：<http://localhost:8000>
- 档案采集应用：<http://localhost:8001>
- 健康检查：`curl -s http://localhost:8001/healthz`

首次启动示范站会写入两条示例公告（`ZFCG-2026-0001`、`ZFCG-2026-0002`）。在档案首页输入公告号即可采集。

停止并保留数据：`docker compose down`；同时删除数据卷：`docker compose down -v`。

## 使用流程

1. 打开档案首页，输入示范站上的公告号，点击“采集公告”。
2. 在示范站打开同一公告：
   - **改稿**：修改标题/正文并保存，站点修订号 +1；再次采集会新增存档版本。
   - **替换附件**：上传新附件，站点修订号 +1；再次采集会留存新附件，旧附件仍可下载。
   - **撤稿 / 恢复**：撤稿后站点对访客隐藏内容；再次采集只更新撤稿状态，不新建版本，历史版本仍可下载。
3. 档案公告页可查看版本历史、逐版正文与附件下载、采集/核对记录。
4. **截标前漏采核对**：在档案首页或“漏采核对”页发起，系统逐页读取示范站目录并与档案快照对照，按现有“采集公告”入口补采清单中的公告。

## 漏采核对（目录代次一致性）

档案员需要找出“源站已有、档案却没收齐”的公告。核对流程在 `ReconcileService` 中实现，保证整份结果只描述**同一目录代次**与**同一份已提交档案状态**：

1. 先在单个只读事务（SQLite WAL 快照隔离）中冻结档案全部公告的最高修订与撤稿标记；
2. 再逐页读取源站目录 `GET /api/catalog`，每页带单调递增的 `generation`（目录代次）；
3. 任一页的代次、总数或总页数与首页不一致，或出现跨页重复公告号、条目数不符，即判定源站在翻页期间新增/改稿/撤稿——本次**核对未完成，不展示部分清单**，提示重新发起；
4. 任一页读取失败同样判定未完成；核对全程只读，**任何失败都不改动存档**；
5. 全部页面同代次后，与第 1 步的档案快照逐条比对，列出三类差异（按类型、公告号排序）：

| 类型 | 判定 | 清单展示的双方状态 |
| --- | --- | --- |
| 未入档 | 档案中没有该公告 | 源站 rN、撤稿与否；档案“未入档” |
| 修订落后 | 档案最高修订 < 源站修订 | 双方修订号与撤稿状态 |
| 撤稿状态不一致 | 修订相同但撤稿标记不同 | 双方撤稿标记 |

每条差异都带“按现有入口补采”按钮，复用既有 `/capture` 流程（未入档建新版、落后留新版且旧版不动、撤稿不一致仅更新公告级标记）。

**交错采集**：核对翻页期间若另一窗口采入了新版本，由于档案快照在发起任何 HTTP 请求前就已固定，整份清单仍对应同一个已提交的档案状态（快照时点的状态），不会让不同公告行看到新旧混杂的档案；新采集的版本在下次核对时自然体现。核对本身不写任何数据（无日志行、无版本行）。

- 核对页大小由档案端环境变量 `RECONCILE_PAGE_SIZE` 控制（默认 20，范围 1–100）；
- 示范站浏览器目录页大小由 `DEMO_CATALOG_PAGE_SIZE` 控制（默认 10）。

## 一致性规则

采集流程先读元数据、下载附件、再读一次元数据，并要求：

- 两次读到的修订号、正文、附件描述、撤稿状态完全一致（防止采集中途站点改稿）；
- 正文修订号与附件修订号相同；否则整次拒收；
- 附件实际字节长度与 SHA-256 与源站声明一致；否则整次拒收。

与档案比对时：

| 情况 | 行为 |
| --- | --- |
| 修订号更新 | 新增一个存档版本（正文 + 附件同事务写入） |
| 修订号相同、内容一致 | 不重复建版（`unchanged`） |
| 修订号相同、内容不同 | 报告源站冲突（`conflict`），不覆盖旧版 |
| 修订号回退 | 报告冲突，不创建、不覆盖 |
| 同号仅撤稿状态变化 | 更新公告级撤稿标记，不新建版本 |

**不可变与原子性**：版本行（正文、附件字节与指纹）一经写入不再修改；撤稿状态保存在公告级。每个版本的公告行、版本行、附件 BLOB、日志在同一 `BEGIN IMMEDIATE … COMMIT` 中写入，SQLite 开启 WAL + `synchronous=FULL`。写入失败会回滚；进程在提交前被杀死，重启后只会看到完整旧版或没有新版，不会出现半份版本。

## 测试

```bash
pip install -r requirements-dev.txt
python -m pytest -q
```

测试覆盖：

- 首次采集、同修订重复采集、改稿、换附件、撤稿/恢复；
- 正文/附件修订不一致整次拒收；
- 同号不同内容冲突且旧版不变；
- 源站修订号回退；
- 附件 SHA-256/长度不符拒收；
- 数据库写入失败回滚、无半份版本；
- 子进程在事务提交前硬退出（模拟进程中断）后重启无残留；
- 档案 Web 页面、下载、错误提示与健康检查；
- 漏采核对：未入档/修订落后/撤稿不一致三类清单、分页读取、目录代次随每次变更递增；
- 翻页期间新增公告或改稿导致代次变化 → 核对未完成且不展示部分清单；
- 翻页期间读取失败 → 核对未完成、存档不变；
- 翻页期间另一窗口交错采入新版 → 整份结果对应同一档案快照；
- 核对严格只读（任何 INSERT 都会使测试失败）、跨页重复号防护；
- 示范站目录 API 参数校验与浏览器分页。

## 源站 API（示范站）

- `GET /api/catalog?page=N&page_size=M`：分页公告目录，含 `generation`（目录代次）、`total`、`total_pages` 与每条公告的 `number/title/revision/retracted/updated_at`；任何新增、改稿、换附件、撤稿都在同事务内使代次 +1。
- `GET /api/notices/{公告号}`：公告元数据（含修订号、唯一附件描述）
- `GET /api/notices/{公告号}/attachment?rev=N`：附件字节

档案应用通过 `SOURCE_BASE_URL` 指向该站。若接入其他站点，只需实现相同的元数据字段与附件校验语义；漏采核对要求目录接口提供分页与目录代次字段。
